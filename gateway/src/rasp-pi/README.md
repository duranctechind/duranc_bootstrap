# Raspberry Pi gateway installer sources

Plain sources for the Duranc VMS gateway installers that customer Raspberry Pi devices
run. **Edit these, never the compiled `gateway/*.sh.x`** -- those are build output,
regenerated by `.github/workflows/build-rasp-pi-installers.yml` on every push here.

| Source | Compiles to |
|---|---|
| `duranc_gw_rasp_pi.sh` | `duranc_gw_rasp_pi.sh.x`, `duranc_gw_rasp_pi_prod.sh.x`, `duranc_gw_rasp_pi_nas.sh.x` |
| `delayedstart_rasp_pi.sh` | `delayedstart_rasp_pi.sh.x` |
| `doc_container_status_rasp_pi.sh` | `doc_container_status_rasp_pi.sh.x` |

## One script for both boards

Pi 4 and Pi 5 are both aarch64 and run the same `durancai/*-gateway-rasp-pi` image, which
has been a single `linux/arm64` image since 02-09-2026. The retired `_4` / `_5` script
pair differed only in filenames, one `PyYAML==5.3.1` pin and a `:pi5` image tag that no
longer exists; their `delayedstart` and `doc_container_status` copies were byte-identical.

The one real per-board difference is RAM, and the installer measures it: a board with less
than 3 GB gets `NODE_OPTIONS=--max-old-space-size=1024` instead of 2048, substituted into
the compose file at install time. That is the knob to turn for a 2 GB Pi 4, and it can also
be overridden per box from the compose file without a rebuild.

The three installer names differ **only** in their baked-in default mode, so there is still
a single script to maintain. The mode is overridable per run:

```bash
./duranc_gw_rasp_pi.sh.x            # staging (its baked-in default)
./duranc_gw_rasp_pi.sh.x prod       # or by argument
DURANC_GW_MODE=nas ./duranc_gw_rasp_pi.sh.x
```

| Mode | Image | Storage |
|---|---|---|
| `staging` | `durancai/staging-gateway-rasp-pi:latest` | docker volumes `stg-gw-files`, `stg-motion-files` |
| `prod` | `durancai/production-gateway-rasp-pi:latest` | same docker volumes |
| `nas` | `durancai/production-gateway-rasp-pi:latest` | binds under `/local-storage` |

## Why the build runs in CI, in a container

`shc` emits a **native** binary, so an aarch64 `.sh.x` must be compiled on aarch64. The
installation-scripts box is x86_64, and its local `shc` would silently produce binaries
that cannot execute on a Pi at all.

The compile therefore runs on a GitHub-hosted `ubuntu-24.04-arm` runner -- but inside a
`debian:bullseye` arm64 container, not on the runner itself. An shc binary links against
the glibc it was built against, and the runner is glibc 2.39: a binary built there fails on
Raspberry Pi OS bookworm with `GLIBC_2.38 not found`. Bullseye is glibc 2.31, which runs on
Pi OS bullseye, bookworm and trixie alike. The workflow asserts both properties on every
build -- the binary must report `aarch64`, and its highest required `GLIBC_` symbol must be
at or below 2.31 -- then runs the compiled installer with an invalid mode to prove the
payload actually decodes and executes on this architecture.

## Credentials

This repository is public, which is the reason the installers are compiled at all: they
carry a Docker Hub pull credential. The sources here hold only `__DOCKER_HUB_USER__` and
`__DOCKER_HUB_TOKEN__` placeholders, and CI injects the real values from the repository
secrets `DOCKERHUB_PULL_USER` and `DOCKERHUB_PULL_TOKEN` immediately before compiling.

**Never paste a real token into these sources.** Note also that shc obfuscates, it does not
encrypt: a determined reader can recover the token from a `.sh.x`, so the secret behind it
must stay a read-only pull token and nothing more.

## What changed from the retired scripts

- `DurancOy` URLs replaced with `duranctechind` throughout.
- Compose files moved to the current compose spec and now require `docker compose` v2. The
  installer installs the plugin; the old `pip3 install docker-compose==1.28.0` path, with
  its `libhdf5-dev`/`libffi-dev`/`PyYAML==5.3.1` prerequisites and `PATH` edits, is gone.
- The gateway container now mounts `/persistent`. Without it the seeded `MediaMTX.yml`, the
  gateway logs behind `/tmp/logs` and `Workflow.env` live only in the container layer and
  vanish on every watchtower recreate, and MediaMTX crash-loops on the missing config.
- watchtower is scoped with a label, so it can only ever recreate the gateway, and it reads
  `/root/.docker/config.json` by explicit path instead of a `~/.docker/auth.json` symlink
  that `sudo` does not expand as it appears to.
- Cron lines are rewritten through `crontab -` under a `# <DURANC-GW>` marker rather than
  appended to `/var/spool/cron/crontabs/root`. The old substring guard matched the Pi-5
  variant's own entry, so upgrading a board left a stale entry behind.
- `/.scripts` is root-owned `0755`, not `0777`: the delayed-start entry runs from the root
  crontab, and a world-writable script there is a local root escalation.
- The installer refuses a 32-bit userland up front instead of failing deep inside compose
  with `no matching manifest`, installs Docker if it is absent, and validates the compose
  file before starting anything.
